# v0.9.1

A packaging release. Nothing about the companion's behaviour changes, and no memory folder needs
anything done to it.

v0.9.0 published one package, the bundled `openreverie` CLI. That is everything a person needs to
run openreverie themselves, and nothing a program needs to build on it. The four engine packages a
host actually imports, `@openreverie/core`, `@openreverie/memory`, `@openreverie/providers` and
`@openreverie/server`, were never published at all, so the only way to consume them was a path
dependency onto a working copy of this repository. That is not a dependency, it is a shared
directory: it does not survive a branch switch, a second machine, or a continuous integration run.

## The engine packages are published

All five scoped packages now publish alongside the CLI: the four above plus `@openreverie/web`,
which carries the browser interface's built assets.

The publish pipeline packs each package with pnpm before handing the tarball to npm. This is not a
preference. npm does not rewrite the `workspace:*` protocol, and `@openreverie/core`,
`@openreverie/memory` and `@openreverie/server` all declare workspace dependencies on each other, so
publishing them straight from their directories would have put `"@openreverie/memory":
"workspace:*"` on the registry: a manifest nobody can install, on a version number that cannot be
reused. pnpm rewrites those to the concrete version, and the publish step now refuses to upload any
tarball whose manifest still carries a `workspace:` specifier.

The step also skips a version already on the registry rather than failing on it, which makes a
partial publish rerunnable without inventing a version number, and lets a package's first release be
created by hand where npm's trusted publishing requires it.

## The server no longer makes a Worker install a React application

`@openreverie/web` was a hard dependency of `@openreverie/server`, but only the Node static-serving
path ever touches it. A host running `createFetchApp` on Cloudflare Workers would have installed
React, sigma and graphology to serve an interface it never mounts.

It is now an optional peer dependency. A consumer who wants the bundled browser interface installs
it explicitly; a consumer who does not, does not. `resolveStaticDir` now recognises the case where
that peer is absent and says which of the two fixes applies, rather than surfacing a bare
`MODULE_NOT_FOUND`.

## Guards, because these are the mistakes that are expensive to undo

The release test now fails if `@openreverie/server` reacquires a hard dependency on
`@openreverie/web`, if any published package declares a `workspace:` peer specifier, if
`packages/web` is marked private (a recursive publish skips a private package silently, which would
drop it out of a release with nobody noticing), or if the web peer range falls out of step with the
version it ships beside. That last one matters because a caret range on a 0.x version does not cross
a minor: `^0.9.0` refuses `0.10.0`, and the version-parity test reads `version` fields and would
never have looked at a range.

## Verification

`pnpm build`, `pnpm lint` and `pnpm test` all exit 0, with 1,835 tests across 82 files. The publish
loop was dry-run locally against every package, with the upload replaced by an inspection: all five
scoped tarballs contain their `dist/`, and no manifest carries a `workspace:` specifier.

## Known limits

Unchanged from v0.9.0, and worth repeating rather than assuming they were read: session resume has
never run against a real model or a genuinely hibernating process, `GET /api/v1/search` has no
browser interface, session resume has no HTTP route, and search cannot fall back to its keyword half
when embeddings are unavailable. All four are tracked in [BACKLOG.md](../../BACKLOG.md).
