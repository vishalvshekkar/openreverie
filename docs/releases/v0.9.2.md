# v0.9.2

Housekeeping. Nothing about the companion's behaviour changes, and no memory folder needs anything
done to it.

The example data used throughout the documentation, the design notes and the test fixtures has been
standardised on one invented cast and set of places. It was previously a mix of invented examples and
ad hoc ones carried in from early development, which made the docs read as if two different sets of
people and events were being described.

The illustrative strings inside two prompt fragments changed with it (`packages/core/src/tools.ts`'s
commitment tool description and `packages/memory/src/reflection.ts`'s commitment instruction). Those
are examples shown to the model, not logic: what the model is asked to do is unchanged, only the
sample label it is shown alongside the request.

A search test's fixture names were rebuilt at the same time. Those tests turn on one name starting
with the probe string, another containing it mid-word, and a third being the probe exactly, so the
three had to move together to keep testing what they were written to test.

Full suite green: 1835 tests across 82 files.

## Packaging

The five scoped engine packages declare `repository` and `bugs` now, which they did not before.
That is not cosmetic. From this release the workflow publishes them with `--provenance`, and npm
verifies the packed manifest's repository url against the signed attestation before accepting the
publish; with the field missing it answers 422 and the publish fails. They got through at v0.9.1
only because a human created those five names by hand at a terminal, which is what npm requires
before trusted publishing can be configured on a name, and the workflow then skipped versions it
found already on the registry.

The workflow refuses to publish a tarball whose manifest has no repository url now, in the same
place and for the same reason it already refuses one still carrying a `workspace:` specifier. Both
are mistakes a later release cannot repair, because the version number is spent.

## The published history

The same standardisation was applied to every commit in the repository, not only to this one, so
the docs, design notes and fixtures read consistently at any point in the history rather than
changing cast partway through. Commits from 2026-08-15 onward were rewritten, and the tags from
v0.3.1 through v0.9.1 now point at different commit ids.

Two consequences worth knowing. A clone taken before 2026-09-04 will not fast forward onto the new
`main`; re-clone it, or point a local `main` straight at `origin/main`. And the provenance
attestations on the versions already published to npm reference commit ids that are no longer in
the repository. Those tarballs are untouched and still install exactly as before; what is broken is
only the link from a published version back to a commit you can look up here.
