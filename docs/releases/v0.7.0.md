# v0.7.0

Two features and one round of repair. Commitments give the companion a record of what you said you
mean to do, one it can revise rather than only append to. Dreaming lets it revisit your memory on its
own schedule and come back with something. The repair round fixed a keyword search lane that had been
silently dead since it shipped.

Everything below states what is not built alongside what is. The Status section of the README is the
fuller inventory.

## Commitments

A commitment is a bounded thing you said you mean to do. "I'm going to the Nightfall screening on
Sunday." "Come summer I want to start swimming again."

The point is not a todo list. It is that a commitment has **identity**, so it can be corrected. Before
this, an intention was a fact, and a fact can only be appended. A real memory folder ended up holding
four live, mutually contradictory records of one cinema booking, with nothing marking three of them
dead. A commitment is one record that gets revised.

Three operations, kept distinguishable on purpose: recording, revising (which must say what it
revises), and resolving with an outcome (done, dropped, or asked to go quiet). All three work from
both capture paths.

**Two paths in, and the second is the one that has to work.** The live `remember` tool captures
mid-conversation, which depends on the chat model actually choosing to call it. End-of-session
reflection reads the whole transcript and always runs, tools or not. Where the two disagree about the
same commitment, reflection wins, because it has read the whole session rather than one turn of it.

**Stated time is kept as you said it.** A phrase the code can resolve without judgment ("tomorrow",
"Sunday", "in three days") becomes a real window. Anything vaguer ("come summer", "next fall") is not
resolved at all. Instead a model that has read your profile writes a short gloss: what you said, when
you said it, and what it plausibly means where you live. Summer in Bangalore runs roughly February to
May, which is exactly why this is written rather than computed from a season table.

`"next friday"` is deliberately refused. English speakers do not agree on whether it means the coming
Friday or the one after, so resolving it would invent a fact you never stated.

**The bracket selects, the gloss speaks.** A coarse internal time bracket decides only whether a
commitment is worth loading into the session prompt. It is never rendered, never spoken, never shown.
A wrong bracket costs a slightly mistimed mention and can never produce a false statement. The prompt
carries your own words and the gloss, nothing derived.

**There is no overdue state anywhere in the schema.** Not a field, not a computed property, not a
rendered phrase. A commitment whose window has passed with no outcome is simply unresolved, which is
an ordinary and unjudged condition. A test scans for this and fails if anyone adds one.

### What commitments do not do yet

- **"Ask once, then permanent silence" is not implemented.** The design calls for a commitment to
  earn exactly one natural follow-up and then go quiet for good. Nothing currently marks a commitment
  as having been raised in conversation. As an interim stand-in, an unresolved commitment past its
  window stops surfacing on its own after two weeks. That preserves the guarantee (the companion does
  not nag) by a different mechanism than the design names.
- **No browser view.** Commitment nodes appear generically in the graph atlas and nowhere else. The
  Record-section list of what is open, resolved and quiet is not built.
- **An open-ended "someday" commitment is invisible to the live companion.** Nothing indexes
  commitments for search or tool lookup, so a commitment with no stated time at all never reaches the
  conversation. Reflection still sees it at session end, so it stays revisable and resolvable.
- **"After the wedding" cannot be expressed.** The record and the graph vocabulary support a
  commitment that waits on something else, but the tool does not offer it, because nothing yet
  reactivates a commitment when the awaited thing happens. Offering a field that nothing can unset
  would let one call silence a commitment permanently.

## Dreaming

A background process that goes back over your stored memory on its own schedule, without you starting
a conversation, and writes back a short narrative plus a set of hedged insights the companion can draw
on later. Each run picks a couple of distant, unrelated-looking things (an old arc, a person you have
not mentioned in months, a session from another season) and looks for a real connection.

**Off by default.** Dreaming spends money on model calls that run whether or not you asked in that
moment, so it stays opt-in. Turn it on with `enabled = true` under `[dreaming]` in `config.toml` and
choose `daily` or `weekly`. The config file is the only switch; it cannot be enabled from the browser.

Four triggers: after a session's reflection finishes, in the background at startup, from the server's
own timer every 30 minutes under `reverie web`, or on demand with `reverie dream`. However many fire,
**at most one dream runs per cadence period**, and missed periods are never made up. A machine off for
two weeks on a daily cadence produces one dream, not fourteen. Dreaming also stays quiet until your
memory holds at least 5 reflected sessions.

**A dream can decline to write its narrative.** A tone gate sits between the model's output and the
file. When what came back does not hold the tone the design intends, the narrative is withheld:
`dream.md` is simply absent, `insight.md` is still written, and the browser says plainly that no
narrative was written for that run. A dream that produced nothing worth reading says so rather than
publishing it anyway.

**Exploration is read-only and bounded.** The run walks your memory through a tool loop that can only
read, never write, with a fixed budget. When a run exhausts that budget it records the fact rather
than quietly returning less. Dreaming makes **no graph writes of any kind** in this version, which is
deliberate: a background process that edits the record while you are not looking is not something to
ship before the output has been read by a human.

**Selection is seeded and deterministic.** Candidates are weighted by staleness against significance,
paired, and walked across the graph with a seeded PRNG, so a run can be reproduced from its seed. Each
run's `process.jsonl` records which seeds were picked and why, what the tool loop looked at, and what
each model call returned.

**Only one dream at a time.** A filesystem lock prevents two processes from dreaming at once, with
takeover if a previous holder died, and an unparseable lock is treated as stale rather than wedging
the feature. The lock lives outside the memory repository, so it never lands in your git history.

**The insights are guesses, and are labelled as such.** Each is hedged and points at the specific
document, session, or graph entity it came from. Mark one right, wrong, or "do not bring this up" from
the web Dreams view, or just react in conversation and the companion records it through a
`dream_feedback` tool. A rejected insight does not come back.

**Dreams are searchable.** `dream` and `dream_insight` are real document kinds, indexed with date
spans like any other, so past dreams and insights come back through `search_memory` and can be filtered
by date. (Worth noting the contrast: commitments are not indexed, which is why an untimed one is
invisible to the live companion.)

### Settings, and where they live

The split is by whether a setting spends money or changes how something reads.

`config.toml`, under `[dreaming]`: whether it is on, the cadence, which triggers fire, caps, and an
optional `models.dreaming` so dreaming can run on a different (usually cheaper) model than
conversation.

`profile.md`, under dreams: the narrative **voice**, which is configurable across first, second and
third person and defaults to first; whether the session opener may mention a fresh dream; and whether
the prompt section appears at all.

**Nothing is rewritten.** `dream.md`, `insight.md`, and a run's `process.jsonl` audit trail are
written once and never edited. `dreams/log.jsonl` is append-only, the same posture as `graph.jsonl`.

Read dreams back with `reverie dream --list` and `reverie dream --show <id>`, or from the browser's
Dreams tab.

### What dreaming does not do yet

- **No human has read a dream a real model wrote.** The pipeline is covered end to end by the
  automated suite (selection, the tool loop, schema validation and retry, scheduling, feedback, the
  CLI, the server endpoints, the web view), all against scripted fake providers. Whether a narrative
  reads well, whether an insight is actually a good one, and whether the tone lands are unreviewed.
  The dreaming machinery is tested. The dreaming output is not.
- The prompt section surfaces the most **recent** insights, not the most relevant to the current
  conversation. There is no relevance ranking.
- The terminal reads dreams and shows verdicts already recorded, but has no command for recording new
  feedback. That is the browser or conversation only. This is a stated deviation from the design,
  which had `reverie dream --show` recording a verdict; it ships display-only.
- **No graph writes.** A dream never adds a node or an edge, by design for this version.
- No consolidation across dreams, no dream series, no way to ask for a dream about something specific,
  and feedback does not yet change what future dreams select.

## Retrieval, repaired

**The keyword half of search had been returning nothing since it shipped.** `toFtsQuery` joined query
terms with a space, which SQLite's FTS5 reads as an implicit AND, so every term had to appear in the
same short chunk. The `search_memory` tool asks the model to write queries "in plain language", so it
duly wrote 10 to 15 token sentences that matched nothing. Every real search had been running on vector
similarity alone.

Measured against a new evaluation harness on a fixture corpus, on the queries a model actually writes:

| | before | after |
|---|---|---|
| recall@5 | 0.79 | **0.88** |
| queries where the keyword lane returned nothing | 20 of 24 | **0 of 24** |

Alongside that:

- **Search results now carry dates.** The index had recorded a date span per document since v0.6.0 and
  never returned it, so every passage reached the model undated.
- **A document returns its matching passages, not just one.** Fusion still ranks by document, but the
  payload now carries up to three matched chunks. The live failure that prompted this: a session
  summary held both "tickets are booked for Sunday 23 August at 6:45pm" and a vaguer undated line
  about the same booking, the document was retrieved, and only the vague line came back.
- **Passages are returned verbatim.** Both lanes previously returned a truncated rendering (a 12 token
  window, or the first 200 characters) rather than the indexed text.
- A recency tiebreak on exact score ties, which never overrides a genuine relevance difference.

Reranking was deliberately not added. A reranker layered on a dead keyword lane measures the wrong
thing. It is recorded in `BACKLOG.md` with the constraint that matters: memory content may not reach
any service other than your configured model provider, which rules out hosted rerankers.

## Other fixes

- **A stated event time now reaches the model with the date it was said.** "Tonight" recorded on the
  16th and retrieved on the 22nd used to read as tonight.
- **An empty event time no longer fabricates one.** A model emitting `eventTime: ""` rather than
  omitting the field produced `(eventTime: "", as stated on 2026-08-20)` in the search index: a claim
  that you stated a time when you stated nothing. Now normalized at both the write and the read
  boundaries, so a hand-edited memory folder is handled too.
- **The prompt no longer treats an intention as evidence it happened.** A session opened by asking how
  a film had been, the day before the screening.
- **Five of thirteen tools leaked their internal function name** instead of a plain notice, printing
  `[using: update_profile]`. All thirteen now have one, guarded by a test that fails if a new tool
  ships without it.
- **`/mode` with no argument now offers a picker** instead of silently swallowing the next line typed.
- **Session directory names are read as local dates in tests, not UTC**, fixing a suite that failed for
  five and a half hours a day in any positive-offset timezone.
- A system prompt assembler that could not be given a fixed clock, which left one test failing for
  three days and rotting by design.
- **The browser's Dreams settings never saved.** Every change to voice, opener mention, or prompt
  section came back `400` because the profile patch schema was never extended, and the read path never
  returned the saved values, so the panel showed defaults whatever you chose. Both sides are fixed,
  with the merge shallow so changing one preference no longer drops the other two.
- **The graph vocabulary is now single-sourced.** Node and edge types were hand-copied into four
  places across three packages. Adding a type to one and not the others made the server fail its own
  outbound validation and return `500` for the whole graph snapshot, taking the atlas down. The
  schemas now derive from one exported list, with parity tests guarding the copies that cannot import
  it.

## Upgrading

A memory folder created before v0.6.0 still needs `reverie migrate` once. Nothing in v0.7.0 requires a
migration of its own.

The search index gains richer chunk text for stated event times. It is derived and rebuildable, so it
updates as documents are reindexed; `reverie reindex` refreshes it in one pass.

Dreaming is off until you turn it on.

## A note on prompt size

The system prompt's stated character budget rose from 28000 to 30600 across these two features, each
raise deliberate and argued in the code. That number is the sum of per-section caps: a worst case in
which every section hits its ceiling simultaneously, which almost certainly never happens. No real
assembled prompt has ever been measured. That gap is recorded in `BACKLOG.md`, and measuring one is
the recommended next step before anyone decides whether the ceiling should bind harder.
